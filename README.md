# 长截图分享服务（分屏凭条方案）

为售后 App 的滚动长截图分享提供本地 HTTP 服务。输入是短字符串组成的若干屏
（无图像识别），输出是收件人可凭**分享号 + 一次性口令**实际打开的、逐格脱敏的
分屏凭条。只依赖 Python 3 标准库。

## 先回答题面问题

> 滚动截屏里的“周一”出现三次，客户分享出去的是哪天那笔订单？

“周一”只是 cell 上的**文字**，不是身份。服务为每个 cell 推断稳定的记录标识
`record_id`：测试场景 D 里三个“周一”分别落在全局位置 0、断缝后的 2、再断缝后的
2，得到三个互不相认的身份 `P0 / s1P2 / s2P2`。客户在**第二屏点选的那一笔**
（`s1p2` → `s1P2`）才是被分享的订单；另外两处同字“周一”因记录身份不同且未授权，
在出具时逐格遮盖（`mask_reason=not_authorized`），其文字不会出现在收件人页面里。
系统从不按文字匹配把同名订单签成同一笔。

## 核心模型

1. **屏 = 独立吸顶栏 + 固定行数正文。** 吸顶栏只随页透传，不参与滚动对齐、不参与
   凭证认证，因此正文里出现同字也不会被吸顶栏干扰。
2. **滚动距离是范围 `[min, max]`。** 相邻两屏枚举候选滚动量 `d`，候选必须让重叠区
   正文文字逐格一致；一个 cell 在全部存活候选里指向同一记录才是 `certain`，否则
   `uncertain`，不确定格上的凭证不认证、私注仍遮盖。
3. **补拍定位记号是硬证据。** 记号规则：同一记录位置不得有两个名字；同一个名字不得
   落在两个位置；`P{n}` 名必须落在该屏第 n 个全局位置。记号与某候选冲突即否决该
   候选；全部候选被否决时该转缝判为**断缝（broken）**，两侧各自生根，绝不签成同一笔。
4. **角色与身份分离。** 客户对具体 `cell_id` 点选 `voucher`（公开凭证）或 `note`
   （私人备注）。角色沿“确定的同一记录”传播到后续屏的重复行；再用文字兜底，保证
   断缝/不确定区里同字私注不漏遮。身份（`record_id`）决定“是不是同一笔、有没有授权”，
   角色决定“这一格怎么遮盖”。
5. **遮盖是逐格的，不允许整页涂黑。** 私注格永远遮盖；凭证格按授权记录决定可见/
   遮盖；普通正文保持可见。若一页正文会被全部遮盖，服务端直接
   `409 REFUSE_FULL_BLACKOUT` 拒绝出具。
6. **拼接不确定就不能发。** 一份分享请求的页面若跨越 broken 转缝，或要求认证的记录
   没有以确定身份出现，返回 `409 UNCERTAIN_STITCH_CANNOT_SEND`，并提示分开出具、
   补拍记号或缩小授权——而不是硬签或涂黑。

## 营业选择：分屏凭条

题目两选一，本实现选**分屏凭条**：

- 保持各屏原顺序，每页标注 `source_screen` 引用来源屏；
- 有歧义的重叠区不强行拼接，按页分开，只遮盖该页确知该遮的格；
- 同一私人成分在多处出现时，靠“记录传播 + 文字兜底”双重保证不漏；
- 已知的公开凭证在授权记录内留足、带 `certified`；
- 收件人接口只返回脱敏后的页面快照，制作台的原屏、分析结构、点选记录一概不出现在
  响应中。
- 客户后续可对已出具的分享**申领只含某一确定行的第二张凭条**（如“只含丙”），
  生成只含该行的子分享并保留来源引用；私注行和不确定行禁止申领。

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/recordings` | 建录屏：`viewport_rows`、`scroll_range:[min,max]`、`screens:[{header,body:[...]}]` |
| POST | `/recordings/{id}/marks` | 补拍定位记号：`marks:[{screen,slot,record}]`，重算对齐 |
| POST | `/recordings/{id}/select` | 客户点选具体行：`{cell_id, role: voucher|note}` |
| GET  | `/recordings/{id}` | 制作台视图（含原屏，仅店员侧） |
| POST | `/recordings/{id}/shares` | 出具分屏凭条；可带 `pages / entitlements / certify` |
| GET  | `/shares/{id}?token=...` | **收件人**打开，只返回脱敏页面 |
| POST | `/shares/{id}/claim` | 收件人申领只含一行的子凭条：`{token, cell_id}` |

错误码：`UNCERTAIN_STITCH_CANNOT_SEND`（拼接不确定/跨断缝）、
`REFUSE_FULL_BLACKOUT`（整页会被涂黑）、`REFUSE_PRIVATE_CLAIM`（私注不能申领）、
`IDENTITY_UNCERTAIN`（该行身份未定，需补拍）、`BAD_TOKEN`（口令无效）。

数据落在 `LSHOT_DATA`（默认 `./data/lshot.json`），分享与录屏持久化；重启后重算
确定性分析，分享号 + 口令依旧可打开。

## 运行与测试

```bash
python3 server.py            # 启动，默认 127.0.0.1:8321
python3 test_lshot.py        # 端到端测试：起停本地服务两次，覆盖重启复查
```

测试覆盖（50+ 断言）：

- **场景 A 基准打通**：四行视口、固定下滚两行；收据七跨屏可读且认证，私注七在两屏
  （含下一屏重复行）都遮盖；丙、丁等普通正文不涂黑；再申领只含丙的第二张凭条；
  重启后两个分享号都还能打开。
- **场景 B 补拍反证**：同屏同滚动证据，仅靠补拍记号证明第二屏同字“收据七”是另一处
  记录 → 转缝断、跨屏分享被拒、第一笔的具体行保住；随后只缩小该收件人授权，
  新分享里连“收据七”文字都不出现，旧分享授权不变。
- **场景 C 两种对齐**：完全重复正文使 d=1/d=2 都成立，第二屏全部不确定、不能认证；
  补一个定位记号后只剩 d=2，确定可发。
- **场景 D 三个“周一”**：三次同字对应三个记录身份，跨断缝拒绝整本发，单屏只发选中
  那笔，另两处同字订单遮盖且文字不可见。
- **场景 E 安全边界**：无/错口令 403、坏分享号 404、收件人响应无原屏结构与私注原文、
  整页涂黑被拒、私注不能被申领。
