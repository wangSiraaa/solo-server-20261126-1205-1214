# 茶餐厅后厨服务（逐份跟单模式）

一台本机即可开门营业的后厨 HTTP 服务，用标准库 `http.server` + `sqlite3` 写成，
无第三方依赖。三个角色各用各的请求操作同一份落盘数据。

## 经营方式：逐份跟单（per-portion tracking）

题面给了两种经营方式，本服务选**逐份跟单**：

- 一张点菜单只代表一份（一次下三份 = 三张独立菜单），可以单独改/撤其中一份。
- 喊炒时同做法进同一口锅，锅里每个 portion 都**钉死一张点菜单号**，
  之后撤单、换桌、移菜都改不动这份已经下锅的事实。
- 起锅时每个 portion 落成一个带**盘号**的成品，盘号始终能反查到原菜单、原食客。
- 撤菜后做熟的那盘转 **余菜（LEFTOVER）**，不再能派给任何桌。
- 已派盘上桌的菜不能撤单退款。
- 已喊炒后改做法（如改免葱而锅里已有葱）：原份留锅转余菜，给同一食客
  另开一张新做法的单等下一锅——这就是"这份改菜来不及了"的可对客解释。

数据链：`食客 diner → 点菜单 slip → 锅里 portion → 盘 plate → 派盘 delivery`，
每一环都有可查的编号（D/M/W/P/V）。

## 三种端与主要接口

| 角色 | 接口 | 作用 |
|---|---|---|
| 服务员 | `POST /diners` | 开台食客 |
| 服务员 | `POST /orders` | 下单，`qty` 份即 `qty` 张独立菜单 |
| 服务员 | `POST /slips/modify` | 喊炒前改某一份的做法 |
| 服务员 | `POST /slips/revise` | 喊炒后改做法：旧份转余菜，另开新单 |
| 服务员 | `POST /slips/cancel` | 撤菜；已派盘拒绝、熟品转余菜 |
| 服务员 | `POST /slips/transfer` | 把一道菜移给另一桌的食客 |
| 服务员 | `POST /diners/move` | 食客换桌，未派的原份跟着走 |
| 服务员 | `GET /tables/{桌}/bill` | 桌账，只列实际交到该桌的菜 |
| 炒档 | `GET /queue?prep=` | 拉待炒队列 |
| 炒档 | `POST /wok/call` | 喊炒，同做法同锅，每份钉菜单号 |
| 炒档 | `POST /wok/finish` | 报熟；`reported` 缺报的份记 SHORT，菜单退回重炒 |
| 炒档 | `GET /wok/{id}` | 查锅：各 portion 的菜单、状态、盘号 |
| 传菜 | `POST /plates/deliver` | 按盘号派盘（支持 `Idempotency-Key`） |
| 传菜 | `GET /plates/{id}` | 查盘号来路与归属 |
| 传菜 | `GET /leftovers` | 余菜清单 |

## 关键不变量如何保证

1. **喊过的锅不能凭空少一份**：portion 在 `/wok/call` 时落库并钉 `slip_id`，
   撤单只改 slip 状态，不删 portion；起锅照样出盘，只是状态变成 LEFTOVER。
2. **只派真做完的锅**：派盘要求盘存在且 `status='READY'`，SHORT 的份根本不生成盘。
3. **余菜不重派 / 已派不退款**：LEFTOVER 派盘 409；DELIVERED 的单撤菜 409。
4. **并发抢盘唯一归属**：派盘用
   `UPDATE ... WHERE status='READY'` 的 CAS，配合全局写锁，两个同时请求只有一个赢。
5. **桌账只认实交**：bill 只从 `deliveries` 表取，余菜/未派都不出现。
6. **丢回应可重连查回**：带同一 `Idempotency-Key` 重试返回同一笔 delivery，
   不产生第二笔；也可随时 `GET /plates/{盘号}` 查那次派盘。
7. **重启可查**：每次写请求提交并 `wal_checkpoint(TRUNCATE)` 回写主库；
   启动时清理可能盐值失配的陈旧 `-shm/-wal` 再恢复，`kill -9` 也不丢已提交数据。

## 跑起来

```bash
python3 kitchen.py --port 8617          # 开门
bash demo.sh                            # 自动从空店重放整个午市并重启查回
```

`demo.sh` 重放的午市覆盖：一次三份分别改/撤、食客换桌、甲乙同锅甲撤单丙加入、
乙丁同锅各派一盘、喊炒后改免葱、炒档少报一份、两传菜员同时抢最后一盘、
派盘丢回应幂等重放、结桌账、以及重启后凭桌号/锅号查回。

演示里出现的 409/404 都是**预期内的业务拒绝**（余菜不可派、已派不可退、
抢盘落败、盘号不存在），不是程序错误。

## 午市结账（demo 实际结果）

- **乙桌**：2 盘 —— 甲乙那锅的豉油皇炒面（P0003）、乙丁那锅的星洲炒米（P0005）。
- **丙桌**：1 盘 —— 丙单独那锅的豉油皇炒面（P0004）。
- **余菜 2 盘**：甲撤单留下的 P0002（W0002）、乙改免葱留下的 P0007（W0005），
  均标 LEFTOVER，不可再派。
- 甲桌账为 0（撤的那份成了余菜，没交到甲桌）。
- 少报那锅：子的菜单 M0014 退回队列 ENTERED 等重炒，系统里不存在第二个盘。
